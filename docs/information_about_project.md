**Версия:** 2.1 — исправленная редакция **Тип:** Высоконагруженная университетская социально-образовательная веб-платформа **Команда:** 4 разработчика **Завершение функциональной разработки:** 04.11.2026 **Тестирование и стабилизация:** 05.11–12.11.2026 **Защита проекта:** 19.11.2026 

# **1. Назначение проекта** 

«ПТУ-Сошиал» — единая платформа, связывающая учебную деятельность, общественную жизнь университета, академические показатели студентов, рейтинги и систему игровых достижений. 

Платформа предназначена для: 

- студентов; 

- преподавателей; 

- организаторов мероприятий; 

- сотрудников учебной части. 

Основные задачи: 

1. Цифровизация учебных заданий и процесса их проверки. 

2. Формирование академического рейтинга студентов. 

3. Учёт учебной и общественной активности. 

4. Проведение индивидуальных и коллективных мероприятий. 

5. Мотивация студентов через батл-пасс и виртуальные награды. 

6. Организация обращения студентов в учебную часть. 

7. Формирование рейтингов и публичной ленты достижений. 

8. Обеспечение безопасности, масштабируемости и надёжности. 

Платформа должна поддерживать добавление новых функций без существенного изменения существующей архитектуры.

# **3. Пользователи и полномочия** 

## **3.1. Основные роли** 

|**Роль**|**Возможности**|
|---|---|
|Студент|Задания, АР, мероприятия, БОА/БУА, батл-пасс, отзывы, справки|
|Преподаватель|Работа с назначенными дисциплинами, создание и проверка заданий, активности,<br>оценивание|
|Организатор|Создание мероприятий, регистрация участников, подтверждение активности|
|Учебная часть|Администрирование системы, создание преподавателей, назначение дисциплин,<br>управление учебной структурой, обработка справок|



#### **Учебная часть является административным подразделением системы.** 

Отдельный пользовательский кабинет администратора не требуется. Административные функции реализуются в кабинете учебной части. 

При необходимости конкретным сотрудникам учебной части назначаются дополнительные полномочия. Например, один сотрудник управляет преподавателями, другой обрабатывает справки. 

## **3.2. Староста** 

Староста не является отдельной ролью. 

В принадлежности студента к группе хранится признак: 

```
isGroupLeader = true/false
```

Старосту назначает преподаватель, закреплённый за соответствующей группой. 

Староста может: 

- подтверждать заявки студентов своей группы; 

- добавлять свою группу на коллективные мероприятия; 

- просматривать состояние групповой регистрации. 

Староста не может самостоятельно назначать себе или другим пользователям дополнительные полномочия. 

Преподаватель может снять признак старосты. 

Все изменения фиксируются в журнале. 

# **4. Управление преподавателями** 

## **4.1. Создание преподавателя** 

#### **Самостоятельная регистрация преподавателей полностью запрещена.** 

Преподавателей создаёт учебная часть через административный интерфейс. 

При добавлении преподавателя сотрудник учебной части указывает: 

- ФИО; 

- электронную почту; 

- кафедру; 

- одну или несколько учебных дисциплин; 

учебные группы, в которых преподаватель ведёт соответствующие дисциплины. 

### **Последовательность** 

1. Сотрудник учебной части открывает раздел «Преподаватели». 

2. Нажимает «Добавить преподавателя». 

3. Заполняет данные. 

4. Выбирает дисциплины и учебные группы. 

5. Сохраняет приглашение преподавателя. 

6. Система отправляет на email одноразовую ссылку для подтверждения и установки пароля. 

7. После подтверждения создаётся активная учётная запись преподавателя. 

До завершения подтверждения хранится приглашение, но не активная учётная запись пользователя. 

Таким образом, сохраняется общее правило: **неподтверждённая учётная запись пользователя не существует** . 

Для преподавателей, испытывающих трудности с использованием компьютера, учебная часть самостоятельно выполняет все административные действия по регистрации и назначению дисциплин. 

Пароли не должны пересылаться сотрудниками через обычную электронную почту или храниться в открытом виде. 

## **4.2. Закрепление дисциплин** 

Один преподаватель может вести несколько дисциплин. 

Например: 

|**Преподаватель**|**Дисциплина**|**Группа**|
|---|---|---|
|Иванов И. И.|Программирование|ИС-21|
|Иванов И. И.|Базы данных|ИС-21|
|Иванов И. И.|Программирование|ИС-22|
|Петров П. П.|Математика|ИС-21|



Также одна дисциплина может быть закреплена за несколькими преподавателями. Назначения выполняет **только учебная часть** . 

## **4.3. Модель закрепления** 

Создаётся сущность `TeacherAssignment` . 

Поля: 

- идентификатор преподавателя; 

- идентификатор дисциплины; 

- идентификатор учебной группы; 

- идентификатор семестра; 

- статус назначения; 

- дата назначения. 

Таким образом, связь строится по принципу: `Преподаватель ↔ Дисциплина ↔ Группа ↔ Семестр` Это позволяет преподавателю вести несколько дисциплин в нескольких группах без смешивания учебных данных. 

## **4.4. Ограничения преподавателя** 

Преподаватель может: 

- создавать задания только по назначенным дисциплинам; 

- выбирать только закреплённые группы; 

- проверять работы своих студентов; 

- выставлять оценки в пределах своей нагрузки; 

- подтверждать регистрацию студентов закреплённых групп; 

- назначать старост в этих группах. 

Преподаватель не может самостоятельно закрепить за собой новую дисциплину. 

## **4.5. Изменение учебной нагрузки** 

Учебная часть может: 

- добавлять дисциплины; 

удалять назначения на будущие периоды; 

- менять учебные группы; 

изменять назначения на текущий семестр с журналированием; 

- просматривать историю преподавания. 

Удаление назначения не должно уничтожать задания, оценки и историю учебной деятельности. 

# **5. Регистрация студентов** 

## **5.1. Заявка** 

При самостоятельной регистрации студент указывает: 

ФИО; 

email; 

пароль; 

- факультет; 

учебную группу. 

После отправки создаётся объект `RegistrationRequest` . 

Запись `User` не создаётся. 

## **5.2. Подтверждение электронной почты** 

Перед рассмотрением принадлежности к группе студент подтверждает email. 

Система отправляет одноразовый код на указанный адрес. 

**Коды подтверждения хранятся в Redis.** 

## **5.3. Хранение кодов в Redis** 

Для каждого запроса подтверждения создаётся запись с ограниченным сроком действия. 

Предлагаемый формат ключа: 

```
email_verification:{requestId}
```

В Redis хранится защищённое проверочное значение кода, а не исходный код в открытом виде. Рекомендуемый срок действия — 10 минут. 

Проверочный код должен: 

создаваться криптографически стойким генератором; 

- иметь срок действия; 

быть привязан к конкретной заявке; 

- использоваться только один раз; 

удаляться либо становиться недействительным после успешной проверки. 

## **5.4. Ограничения подтверждения** 

Предлагаемые ограничения: 

- не более 5 неверных попыток на один код; 

- не более 3 отправок кода в течение 15 минут на заявку; 

- минимальный интервал между повторными отправками — 60 секунд. 

После превышения лимита проверка временно блокируется. 

При повторной отправке предыдущий код становится недействительным. 

Истечение срока действия кода не должно приводить к созданию пользователя. 

При временной недоступности Redis подтверждение не выполняется в обход проверки. 

## **5.5. Подтверждение группы** 

После успешного подтверждения email заявка становится доступна: 

- преподавателю, закреплённому за группой; 

- подтверждённому старосте этой группы. 

После одобрения выполняется транзакция: 

1. Проверяется актуальность заявки. 

2. Проверяется уникальность email. 

3. Создаётся пользователь. 

4. Пользователю назначается роль студента. 

5. Создаётся принадлежность к группе. 

6. Заявка получает статус «Подтверждена». 

Если операция не выполнена полностью, учётная запись не создаётся. 

## **5.6. Тестовая отправка почты** 

Для локальной разработки можно использовать Mailpit как почтовую песочницу. 

В демонстрационной версии коды будут отображаться в тестовом почтовом интерфейсе. 

Для настоящего развёртывания необходим настроенный почтовый провайдер. 

# **6. Академический рейтинг** 

## **6.1. Начальное значение** 

При начале семестра: 

```
АР = 0
```

АР начисляется студенту за принятые преподавателем учебные работы. 

## **6.2. АР по дисциплинам** 

Каждая дисциплина имеет отдельный академический рейтинг студента. 

Общий АР текущего семестра является суммой предметных показателей. 

Для MVP предлагается ограничение в 1000 общего АР за семестр. 

## **6.3. Создание задания** 

Преподаватель выбирает одну из закреплённых дисциплин и соответствующие учебные группы. 

Указывает: 

- название; 

- описание; 

- дедлайн; 

- максимальное количество АР; 

- материалы; 

- возможность поздней сдачи. 

Система запрещает создавать задания по неназначенным дисциплинам. 

## **6.4. Оценивание** 

Количество АР зависит от выставленной оценки. 

Начальная таблица коэффициентов: 

||**Оценка**|**Коэффициент**|
|---|---|---|
|5||1,00|
|4||0,75|
|3||0,50|
|2||0,00|



Коэффициенты настраиваются учебной частью. 

## **6.5. Уменьшение награды после дедлайна** 

После дедлайна потенциальная награда постепенно уменьшается. 

Для первой версии предлагается скорость 1% в сутки, с расчётом по фактическому времени просрочки. 

Максимальное уменьшение — 50%. 

Формула: 

```
База = Максимальный АР × Коэффициент оценкиКоэффициент времени = max(0.5, 1 − 0.01 ×
дни просрочки)Итоговый АР = floor(База × Коэффициент времени)
```

Пример: задание стоимостью 100 АР принято с оценкой 5. 

||**Просрочка**|**Начисление**|
|---|---|---|
|Нет||100|
|1 день||99|
|5 дней||95|
|10 дней||90|
|20 дней||80|



Время проверки преподавателем не учитывается при расчёте опоздания. Учитывается время отправки принятой версии работы. 

АР начисляется только один раз за принятую работу. 

## **6.6. Доработка** 

Преподаватель может вернуть работу с комментарием. 

Студент повторно отправляет исправленный вариант. 

В случае принятия учитывается время отправки именно принятой версии. 

## **6.7. Связь с батл-пассом** 

Каждое подтверждённое начисление АР увеличивает опыт батл-пасса текущего сезона. 

Начисление АР и обновление опыта выполняются согласованно, без потери или дублирования операций. 

## **6.8. Завершение семестра** 

После завершения семестра: 

- текущий АР закрывается; 

сохраняется итог по дисциплинам; 

- формируется архив; 

начинается новый семестр с нулевыми значениями. 

# **7. БОА и БУА** 

БОА — баллы общественной активности. 

БУА — баллы учебной активности. 

Тип баллов указывается создателем мероприятия. 

Преподаватель или организатор может назначать участнику любое целое количество баллов от 0 до 100 включительно, но не больше максимальной награды мероприятия. 

Баллы начисляются после подтверждения участия. 

Для каждого преподавателя или организатора действует установленный учебной частью бюджет начислений. 

## **7.1. Показатели студента** 

Отдельно сохраняются: 

- БОА текущего семестра; 

- БУА текущего семестра; 

- БОА за всё время; 

- БУА за всё время. 

Смена семестра не уничтожает накопленную статистику. 

## **7.2. Бюджеты** 

Для преподавателей действует ежемесячный лимит начислений по закреплённым группам. 

Для организаторов бюджет назначается учебной частью. 

Начисление сверх лимита запрещено. 

# **8. Мероприятия** 

## **8.1. Форматы** 

Мероприятия бывают: 

- индивидуальные; 

- коллективные. 

Создавать их могут преподаватели и организаторы. 

## **8.2. Индивидуальное участие** 

Студент самостоятельно присоединяется к мероприятию. 

После его завершения организатор подтверждает участие и назначает БОА/БУА. 

## **8.3. Коллективное участие** 

Преподаватель или староста добавляет учебную группу. 

Создатель мероприятия устанавливает минимальный процент желающих участвовать. 

Каждый студент самостоятельно принимает решение об участии. 

Порог рассчитывается по формуле: 

```
Необходимые участники = ceil(Численность группы × Процент / 100)
```

Если к окончанию регистрации нужное количество не набрано, групповая заявка отменяется. 

Если порог достигнут, группа допускается, но баллы начисляются только подтвердившим участие студентам. 

## **8.4. Начисление** 

Организатор указывает каждому участнику индивидуальное количество БОА или БУА от 0 до 100 с учётом максимума мероприятия. 

Дублирование начислений запрещено. 

# **9. Общая внутренняя валюта** 

## **9.1. Источники получения** 

Валюта поступает из двух источников: 

1. Ежемесячная конвертация БОА и БУА. 

2. Вознаграждение за подтверждённый отзыв о мероприятии. 

Источники фиксируются отдельно в истории кошелька. 

## **9.2. Конвертация** 

Базовый предлагаемый курс: 

```
1 БОА = 1 единица валюты1 БУА = 1 единица валюты
```

Ежемесячная конвертация учитывает баллы, заработанные в расчётном месяце. 

При этом рейтинговые БОА и БУА не списываются. 

## **9.3. Валюта за отзывы** 

После завершения мероприятия студент может получить валюту за содержательный отзыв о своём участии. 

Для MVP предлагается: 

**5 единиц валюты за один одобренный отзыв.** 

Количество настраивается учебной частью. 

### **Условия начисления** 

1. Мероприятие завершено. 

2. Фактическое участие студента подтверждено. 

3. Студент оставил оценку и текстовый комментарий. 

4. Комментарий прошёл фильтрацию и модерацию. 

5. Вознаграждение за отзыв этого студента на это мероприятие ранее не выдавалось. 

После выполнения условий валюта начисляется непосредственно в кошелёк. 

### **Ограничения** 

Один оплачиваемый отзыв на одно мероприятие. 

- Редактирование отзыва не даёт новую награду. 

- Удаление и повторная публикация не позволяют получить награду ещё раз. 

- За отклонённый отзыв награда не выдаётся. 

- Нельзя публиковать несколько оплачиваемых отзывов об одном мероприятии. 

- В журнале хранится основание начисления. 

Для защиты от массового получения валюты на фиктивных мероприятиях учебная часть может установить месячный лимит наград за отзывы. 

В рамках MVP предлагается максимум 5 оплачиваемых отзывов в месяц на студента. 

**Валюта за отзывы не является БОА или БУА и не участвует в ежемесячной конвертации.** 

## **9.4. Транзакции** 

Каждое изменение баланса имеет: 

- уникальный идентификатор; 

- пользователя; 

- величину изменения; 

- основание; 

- дату; 

- тип операции. 

Повторная обработка одной операции не изменяет баланс повторно. 

# **10. Фильтрация и модерация комментариев** 

## **10.1. Область действия** 

Фильтрация применяется к: 

- отзывам на мероприятия; 

- комментариям к отзывам, если такая возможность будет добавлена; 

- другим публичным текстовым полям, поддерживающим пользовательские комментарии. 

В текущем MVP обязательной является фильтрация текстовых отзывов. 

## **10.2. Проверки** 

Перед публикацией выполняются: 

1. Проверка длины текста. 

2. Проверка запрещённых слов и выражений. 

3. Проверка ссылок на спам-ресурсы. 

4. Проверка повторяющихся одинаковых комментариев. 

5. Проверка подозрительной частоты публикаций. 

6. Проверка попыток вставки вредоносной разметки. 

7. Базовая проверка на публикацию чувствительных персональных данных. 

Предлагаемая длина комментария — от 20 до 1000 символов. 

## **10.3. Статусы отзыва** 

- Черновик. 

- На проверке. 

- Опубликован. 

- Отклонён. 

- Скрыт модератором. 

## **10.4. Правила модерации** 

Если комментарий проходит автоматическую проверку, он может публиковаться автоматически. 

Если обнаружен потенциально недопустимый контент, комментарий направляется на ручную проверку сотруднику учебной части с полномочиями модератора. 

Неоднозначный текст не должен автоматически считаться нарушением только из-за совпадения отдельного слова с фильтром. 

При отклонении сохраняется причина. 

## **10.5. Связь с валютой** 

Публикация и выдача награды должны быть связаны. 

- Одобренный отзыв — валюта начисляется один раз. 

- Отзыв ожидает модерации — валюта ещё не начислена. 

- Отклонённый отзыв — валюта не начисляется. 

- Редактирование одобренного отзыва — повторная проверка без повторной выдачи валюты. 

Если награждённый отзыв позднее скрыт за нарушение, операция остаётся в журнале. Коррекция валюты производится отдельной подтверждённой операцией согласно правилам модерации. 

# **11. Лента наград** 

Система формирует публичную ленту достижений студентов. 

Для каждой записи отображаются: 

- студент; 

- тип достижения; 

- количество начисленных БОА или БУА; 

- мероприятие или основание; 

- дата. 

Лента доступна авторизованным пользователям. 

## **11.1. Таблицы лидеров** 

ТОП по АР. 

- ТОП по БОА. 

- ТОП по БУА. 

Предусмотреть фильтрацию по группе, факультету и семестру. Обновление таблиц должно учитывать кеширование и изменение баллов. 

## **11.2. Награды лидерам** 

Предусмотреть возможность назначения дополнительных виртуальных наград за высокие места. Автоматическое награждение по окончании семестра не является критической функцией MVP. 

# **12. Батл-пасс** 

## **12.1. Основные параметры** 

- Продолжительность сезона — шесть месяцев. 

- Базовое количество уровней — 50. 

- Максимальное проектное количество — 100. 

- Опыт начисляется за заработанный АР. 

Предлагаемое правило для MVP: `20 АР = 1 уровень` 

## **12.2. Бесплатная дорожка** 

Доступна каждому подтверждённому студенту. 

Награды: 

- виртуальные кейсы; 

- декоративные предметы; 

- рамки профиля; 

- значки; 

коллекционные элементы. 

## **12.3. Премиальная дорожка** 

Приобретается за общую внутриигровую валюту. 

Действует только в рамках текущего сезона. 

При покупке открываются премиальные награды уже достигнутых уровней. 

Премиальный пропуск не влияет на оценки и начисление академического рейтинга. 

## **12.4. Кейсы и инвентарь** 

Кейсы выдаются за уровни батл-пасса. 

Прямая покупка случайных кейсов не предусматривается. 

Кейсы содержат только виртуальные декоративные предметы, не имеющие денежного эквивалента. 

Инвентарь хранит полученные предметы и неоткрытые кейсы. 

Повторная выдача одной и той же награды уровня запрещена. 

# **13. Учебная часть** 

## **13.1. Административные функции** 

Сотрудники учебной части управляют: 

- преподавателями; 

- кафедрами; 

- факультетами; 

- учебными группами; 

- дисциплинами; 

- закреплениями преподавателей; 

- служебными ролями; 

- семестрами; 

- бюджетами начислений; 

- настройками АР; 

- параметрами батл-пасса; 

- модерацией отзывов; 

- заявлениями студентов. 

Доступ к отдельным административным возможностям можно ограничивать внутренними полномочиями сотрудников. 

## **13.2. Обращения студентов** 

Студент может подать заявление на получение справки. 

В заявлении указывается: 

- тип справки; 

- комментарий; 

- способ получения. 

## **13.3. Статусы** 

- Подана. 

- В обработке. 

- Готова. 

- Выдана. 

- Отклонена. 

- Отменена. 

Студент видит актуальный статус своего обращения. 

Учебная часть может изменять статусы в рамках разрешённого процесса. 

## **13.4. Интеграция с 1С** 

Не реализуется. 

В дальнейшем может использоваться для обмена документами и сведениями с университетской системой.

# **16. Проверки и тестирование** 

## **16.1. Регистрация** 

- Неподтверждённая заявка не создаёт пользователя. 

- Преподаватель не может зарегистрироваться самостоятельно. 

- Учебная часть создаёт приглашение преподавателя. 

- Приглашённый преподаватель активирует учётную запись. 

- Redis-код истекает по TTL. 

- Повторное использование кода невозможно. 

- Чужой староста не может подтверждать студентов другой группы. 

## **16.2. Преподаватели и дисциплины** 

- Учебная часть назначает несколько дисциплин преподавателю. 

- Преподаватель видит все назначенные дисциплины. 

- Преподаватель создаёт задания по каждой дисциплине. 

- Преподаватель не может создавать задания по неназначенной дисциплине. Изменение назначений не удаляет исторические оценки. 

## **16.3. Академический модуль** 

- АР начинается с нуля. 

- Начисление зависит от оценки. 

- Просрочка уменьшает потенциальную награду. 

- Время проверки не уменьшает награду. 

- Повторное принятие не дублирует начисление. 

- Доработка учитывает время принятой версии. 

- Архив семестра сохраняет результаты. 

## **16.4. БОА/БУА** 

- Допускается начисление любого целого значения от 0 до 100. 

- Значения вне диапазона отклоняются. 

- Ограничение бюджета соблюдается. 

- При повторном подтверждении баллы не дублируются. 

## **16.5. Отзывы и валюта** 

Отзыв может написать только подтверждённый участник. 

- Запрещённый комментарий отправляется на модерацию. 

- За одобренный отзыв выдаётся валюта. 

- За редактирование повторная валюта не выдаётся. 

- Повторное создание отзыва не даёт повторного начисления. 

- Отзыв, отклонённый модератором, не награждается. 

- При параллельных запросах награда выдаётся один раз.
